# Portfolio research and design rationale

Researched on 9 October 2026 for Kushagra Gupta's portfolio. The intended focus is AI and data science, with an expected 2027 PGP completion at Jio Institute. Profile: [kushagragupta-23 on GitHub](https://github.com/kushagragupta-23).

This research compares eighteen current primary portfolio or personal sites: ten initial references and eight additional references selected from the user's supplied developer-portfolio directory. It studies content hierarchy, project presentation, identity, interaction examples, and authors' design explanations. It does not claim an objective ranking of the world's best portfolios or measured performance scores for the reference sites.

The browsing extraction returned only a thin shell or no substantive body for these samples. That is a limitation of this inspection method, not evidence that their interactive sites are broken, and no detailed design conclusions are drawn from them.

The directory research strengthens four decisions for this implementation:

1. Lead with accurate AI/data science student positioning and actual education.
2. Give the selected projects concise, differentiated purposes, meaningful technology labels, and working repository destinations; keep the archive for the complete collection.
3. Connect skills to actual methods and workflows, and leave unsupported proficiency scores or outcome metrics out of the page.
4. Use an original node-sphere interaction and editorial visual system while keeping reading, navigation, and contact straightforward.

## Applied design direction

The following recommendations are design inferences from the comparisons, adapted to this owner's AI and data science work:

- Use a warm ivory background, burgundy typography, electric yellow accents, generous spacing, and large editorial headings for an original, readable identity.
- Include a small interactive SVG node sphere as a visual expression of connected systems and data. It should enhance the hero without controlling navigation or delaying access to content.
- Establish a clear first-screen identity, concise specialty statement, and visible routes to projects and contact.
- Present six selected project cards when there is enough real, differentiated work, followed by an archive that exposes all public projects. Keep selected cards concise and link to substantive repositories or actual demos.
- Put factual biography, education, skills, and contact information in dedicated sections. Only display résumé, demo, email, or social links when their destinations are known.
- Use short, purposeful interactions and readable responsive layouts. The core content must remain available when JavaScript or animation is unavailable.

Josh Comeau [recommends two to five highlighted projects](https://www.joshwcomeau.com/effective-portfolio/) and explains the value of guiding visitors through a curated selection. Six can still work here if the projects demonstrate different capabilities and remain easy to scan; the archive accommodates the user's request to include all projects.

For AI and data science projects, each card or repository should make the problem, data source, method, owner's contribution, and reproducibility clear. Evaluation metrics and outcomes should appear only when supported by the project. Avoid inferred business impact, invented users, fabricated accuracy numbers, or unsupported employment claims.

Paco's [redesign explanation](https://paco.me/writing/redesign-2021) supports an emphasis on performance, typography, simplicity, and maintenance. This favors a static site with small enhancements rather than a large application architecture for a mostly informational portfolio.

## Quality and deployment criteria

| Area | Implementation criterion | Primary source |
| --- | --- | --- |
| Structure | Use semantic headings and landmarks, a skip link, keyboard-accessible navigation, and appropriate image descriptions | [W3C page structure tutorial](https://www.w3.org/WAI/tutorials/page-structure/) |
| Contrast | Aim for at least 4.5:1 for ordinary text and 3:1 for large text | [W3C contrast guidance](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) |
| Motion | Respect reduced-motion preferences and disable nonessential movement under that preference | [W3C animation guidance](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html) |
| Interaction | Provide clear icon labels and immediate feedback; avoid hover changes that move text; limit expensive blur and continuous effects | [Rauno's Web Interface Guidelines](https://interfaces.rauno.me/) — a living guide containing some explicitly subjective advice |
| Performance | Target LCP at or below 2.5 seconds, INP at or below 200 milliseconds, and CLS at or below 0.1 | [Google Core Web Vitals](https://web.dev/articles/vitals) |
| Hosting | Publish static HTML, CSS, and JavaScript from a public repository on GitHub Free | [GitHub Pages documentation](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages) |

Core Web Vitals are field metrics assessed at the 75th percentile. A local or Lighthouse result is a useful development check, not evidence of real-user INP performance or guaranteed field scores.

GitHub's free user-site address is `https://<username>.github.io`, using a repository named `<username>.github.io`. A project repository uses `https://<username>.github.io/<repositoryname>`. For this account, the user-site repository would be `kushagragupta-23.github.io` and the corresponding address would be `https://kushagragupta-23.github.io`. Availability and existing repository contents must be checked before publishing. The documentation above describes both hosting forms.

Use actual contact links on the static site. A form requires a real submission service; presenting an unconnected submit button would mislead visitors. All personal details and project claims should be grounded in supplied information or verified public sources before deployment.
